## 수정·검증 상태

### 1. 프론트 회원가입 422 — 수정·원격 반영·FE 배포 완료

기존 FE `handleRegister`는 `{ username, password }`만 전송했으며 BE `UserCreate`의 nickname 필수 조건과 맞지 않아 422를 재현했습니다. 원격 FE develop의 기존 코드에도 이 문제가 있습니다.

사용자가 별도 프론트 담당자가 없으므로 AI에게 수정을 맡겼습니다. FE `dev/log-frontend-integration`에서 register.html에 닉네임 입력을 추가하고 auth.js가 `{ username, nickname, password }`를 보내도록 수정했습니다. 비밀번호 조건도 4자에서 BE와 같은 8자로 맞췄습니다. 공백 닉네임·짧은 비밀번호·확인 불일치를 요청 전에 차단합니다. 실제 FE JS 핸들러를 DOM 대역으로 실행하여 임시 FastAPI HTTP 서버에서 가입201·로그인200, Bearer 인증, Mock SSE, 로그 저장을 확인했습니다. 이후 사용자 요청으로 `6fd410e`를 커밋·푸시했고, Aside가 Vercel Production 배포와 가입 화면을 확인했습니다. Codex는 공개 HTML/JS가 해당 커밋과 일치함을 확인했습니다. 사용자가 배포 브라우저에서 실제 가입·로그인에 성공했습니다.

### 2. 전체 스트림 타임아웃 — 로컬 수정·검증, 서버 미반영

수정 전 `asyncio.wait_for()`는 초기 연결만 감쌌습니다. 첫 청크 이후 멈춘 가짜 스트림이 AI 제한을 넘겨 외부 취소가 필요함을 다시 재현했습니다. 현재 로컬 코드는 연결과 각 청크 읽기에 하나의 종료 시각을 공유합니다. 청크가 계속 와도 전체 제한이 늘어나지 않으며, 소비자가 청크를 처리하는 동안 타임아웃이 호출자 작업을 취소하지 않습니다.

기본 제한은 30초이며 SDK 스트림 정리는 별도로 최대 1초입니다. 초기 연결 지연, 첫 청크 전/후 정지, 연속 청크의 전체 시간 초과, 연결·읽기 합산 초과, 정상 완료, 소비자 지연, 호출자 취소, 느린 정리를 가짜 SDK로 검증했습니다. 타임아웃은 기존 SSE 안내·완료 이벤트와 `status=error`, `error_message=AI_TIMEOUT` 저장으로 연결합니다.

### 3. 초기 세션·질문 DB 실패 처리 — 로컬 수정·검증, 서버 미반영

수정 전 실패 주입에서 일반 텍스트 500, 명시적 rollback·`db_save_failed` 누락을 확인했습니다. 현재 자동 생성 세션과 질문은 flush로 ID를 확보한 뒤 한 번에 commit합니다. 질문 저장 실패 시 새 세션까지 되돌리며 기존 세션의 updated_at도 복원합니다. 명시적 `POST /chat/sessions`에도 같은 실패 처리를 적용했습니다.

초기 DB 실패 시 AI를 호출하지 않고 rollback·실패 이벤트 및 HTTP 500 JSON `{"detail":"대화를 저장하지 못했습니다. 잠시 후 다시 시도해 주세요."}`를 반환합니다. 성공 이벤트는 commit 이후에만 기록하며 세션·질문·답변을 request_id와 entity로 구분합니다. DB 실패 로그에는 SQL·파라미터 대신 예외 종류만 기록합니다. 정상 SSE 계약은 유지합니다.

### 4. SDK 초기화 실패의 조용한 Demo 전환 — 재현, 별도 후속

가짜 키가 설정된 대역에서 SDK 생성자를 실패시켜 초기화 로그 없이 성공한 Mock 답변·`ai_call_success`로 처리됨을 재현했습니다. 이 경로는 이번 두 수정의 범위에서 변경하지 않았습니다. 현재 운영에서 실제 AI를 사용한 사용자 시험과 구분하며 현재 서비스 장애로 단정하지 않습니다.

### 5. 요청 남용 제한·운영 JWT 최소 조건 — 구현·격리 검증, 운영 미확인

사용자 후속 요청으로 가입 IP당5회/60초, 로그인·비밀번호 변경 IP당10회/60초, 채팅 사용자당6회·전체20회/60초, 동시 채팅 사용자당1개·전체3개 제한을 구현했습니다. 초과 요청은429·Retry-After·거절 이벤트로 안내하며 질문 저장·AI 호출을 하지 않습니다. SSE·초기 DB 실패·취소 뒤 슬롯 해제를 검증했습니다. 제한은 기존 단일 프로세스 메모리 기준이며 재시작 시 초기화됩니다. 추가 인프라·DB 모델 변경은 없습니다.

production/prod의 공개 기본 JWT 키·빈 값·32바이트 미만 키는 고정 오류로 시작을 막습니다. 키를 자동 교체하지 않습니다. `scripts/check_security_config.py`는 기존 PID의 환경과 작업 폴더를 사용해 boolean만 출력하며 DB·AI에 접근하지 않습니다. 실제 서버의 JWT 키·SSH/포트/IAM/IMDSv2 확인은 Aside 보고가 필요합니다. 기존26개를 포함한 보안 회귀 근거는 최신 작업 결과에 기록합니다.

## 배포 시 다룰 작은 항목

- FE API 주소는 로컬/배포로 분리했고 `DEPLOYED_API_BASE_URL`에 `https://b71chatbe.ddns.net`을 반영·배포했습니다. 미설정 외부 사이트는 요청 없이 안내하며 localhost를 호출하지 않습니다.
- CORS는 모든 출처와 credentials=true 조합. 현재 Bearer 방식에서 실제 Production Origin의 사전 요청·응답 헤더는 통과했습니다. 출처 제한은 별도 후속 설정이며 첫 연결 시험을 위해 서버를 변경하지 않습니다.
- 인증 쿠키 secure=False가 고정. HTTPS 배포 시 True 설정을 검토합니다. 현재 FE는 Bearer를 사용합니다.
- FE `ea431c8`의 마크다운 출력은 DOMPurify로 정제하며 라이브러리 미사용 시 일반 텍스트로 처리합니다. 이전의 정제 미구현 판정은 해소됐습니다. 개편 후 운영 계정의 실제 질문 회귀는 별도 미실시입니다.
- 기존 SQLite의 컬럼을 create_all이 자동 변경하지 않습니다. 모델 수정 시 DB 보존·반영을 함께 처리합니다.

이 항목들을 모두 첫 EC2 생성 전의 점검 절차로 요구하지 않습니다. 실제 연결·변경 단계에서 필요한 것부터 처리합니다.

## 과잉 여부

FastAPI·SQLite·JWT·최근 대화 컨텍스트·사용자 로그는 미션과 직접 연결됩니다. SQLAlchemy와 SSE는 필수 기술은 아니지만 이미 작동하는 구현이므로 제거·재작성할 이유가 없습니다. 여러 세션·통계·비밀번호 변경·풍부한 UI는 미션보다 넓은 기능이지만 첫 배포를 위해 더 확장할 필요는 없습니다.

현 단계의 적정 선택은 기존 구조 유지, 실제 불일치 수정, EC2 한 대, 정적 Vercel, 수동 BE 재배포입니다. Docker·RDS·로드 밸런서·Kubernetes·자동 배포를 추가하면 지금의 학습 목표보다 부담이 커집니다.
