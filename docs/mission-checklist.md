## 우선 보완할 실제 문제

### 1. 프론트 회원가입 422 — 수정·원격 반영·FE 배포 완료

기존 FE `handleRegister`는 `{ username, password }`만 전송했으며 BE `UserCreate`의 nickname 필수 조건과 맞지 않아 422를 재현했습니다. 원격 FE develop의 기존 코드에도 이 문제가 있습니다.

사용자가 별도 프론트 담당자가 없으므로 AI에게 수정을 맡겼습니다. FE `dev/log-frontend-integration`에서 register.html에 닉네임 입력을 추가하고 auth.js가 `{ username, nickname, password }`를 보내도록 수정했습니다. 비밀번호 조건도 4자에서 BE와 같은 8자로 맞췄습니다. 공백 닉네임·짧은 비밀번호·확인 불일치를 요청 전에 차단합니다. 실제 FE JS 핸들러를 DOM 대역으로 실행하여 임시 FastAPI HTTP 서버에서 가입201·로그인200, Bearer 인증, Mock SSE, 로그 저장을 확인했습니다. 이후 사용자 요청으로 `6fd410e`를 커밋·푸시했고, Aside가 Vercel Production 배포와 가입 화면을 확인했습니다. Codex는 공개 HTML/JS가 해당 커밋과 일치함을 확인했습니다. 사용자가 배포 브라우저에서 실제 가입·로그인에 성공했습니다.

### 2. 타임아웃이 초기 연결에만 적용됨

`app/services/gemini_service.py`의 `asyncio.wait_for()`는 `generate_content_stream()` 호출만 감쌉니다. 이후 `async for chunk`에는 시간 제한이 없습니다. 첫 토큰 뒤 응답이 멈추는 가짜 스트림으로 AI 제한 시간을 넘어도 끝나지 않는 현상을 재현했습니다. 검증 코드는 외부 타임아웃으로 취소했으며 실제 Google 요청은 하지 않았습니다.

Chat 담당자가 SDK 스트림 읽기까지 제한하거나 전체 응답 처리에 한 번의 제한을 적용하면 됩니다. 큐·재시도 플랫폼·새 스트리밍 프레임워크는 필요 없습니다.

### 3. 질문·세션 DB 실패 로깅의 빈틈

`app/api/v1/chat.py`에서 SSE 제너레이터 안의 답변 저장은 try/rollback/실패 로깅을 사용합니다. 그 이전의 세션 생성·질문 저장 commit은 같은 처리로 보호되지 않습니다. 초기 DB 저장이 실패하면 필요한 `db_save_failed` 이벤트와 일관된 오류 응답이 누락될 수 있습니다. 이 항목은 코드 읽기로 확인했으며 DB 실패 주입은 하지 않았습니다.

dev/log 후속 작업으로 이 저장 경로에 성공 로그와 rollback·실패 로그·HTTP 오류 처리를 추가할 수 있습니다. 정상 SSE 형식을 바꿀 필요는 없습니다.

## 배포 시 다룰 작은 항목

- FE API 주소는 로컬/배포로 분리했고 `DEPLOYED_API_BASE_URL`에 `https://b71chatbe.ddns.net`을 반영·배포했습니다. 미설정 외부 사이트는 요청 없이 안내하며 localhost를 호출하지 않습니다.
- CORS는 모든 출처와 credentials=true 조합. 현재 Bearer 방식에서 실제 Production Origin의 사전 요청·응답 헤더는 통과했습니다. 출처 제한은 별도 후속 설정이며 첫 연결 시험을 위해 서버를 변경하지 않습니다.
- 인증 쿠키 secure=False가 고정. HTTPS 배포 시 True 설정을 검토합니다. 현재 FE는 Bearer를 사용합니다.
- 마크다운 출력은 `marked.parse()` 결과를 innerHTML에 넣고 별도 HTML 정제가 없습니다. 테스트 범위를 넘어 공개 사용을 늘리기 전 FE에서 정제를 검토합니다. 현재 브라우저 실행 재현은 하지 않았습니다.
- 기존 SQLite의 컬럼을 create_all이 자동 변경하지 않습니다. 모델 수정 시 DB 보존·반영을 함께 처리합니다.

이 항목들을 모두 첫 EC2 생성 전의 점검 절차로 요구하지 않습니다. 실제 연결·변경 단계에서 필요한 것부터 처리합니다.

## 검증 결과와 한계

Python 3.12.13, requirements.txt로 별도 가상환경을 만들고 별도 임시 DB·Mock 모드로 기존 테스트를 실행했습니다. 기존 테스트는 **6 passed**: 인증, 비로그인 차단, 채팅·메시지·로그, 모델 관계, 로그 페이지네이션·필터, 통계입니다. 추가 점검은 nickname 누락 422 재현, 공백 질문 차단, 타 사용자 세션·로그 차단, 스트림 도중 제한 누락 재현입니다.

2026-10-04 Aside 보고상 FE `6fd410e`의 Vercel Ready / Production / Latest 배포와 가입 화면을 확인했습니다. Codex의 별도 읽기 전용 HTTP 확인으로 FE HTML/JS 9개 파일 내용 일치, 실제 FE Origin의 가입·로그인·채팅 스트림·로그 CORS 사전 요청 200, BE healthy/production, 미인증 로그 401을 확인했습니다. 계정·질문은 생성하지 않았습니다.

그 후 사용자가 테스트 계정으로 배포 브라우저 가입·로그인·Demo 질문·로그 재조회에 성공했고, EC2에 Google AI Studio 키를 직접 입력했습니다. Aside가 서비스 재시작과 active/healthy를 보고했습니다. 사용자가 전달한 실제 답변 및 로그 화면에서 철근·콘크리트 역할 설명과 같은 대화의 후속 표 정리, 질문·답변 로그 저장을 확인했습니다. 이는 사용자 브라우저 시험 근거이며 Codex의 Google 프로젝트 사용량 조회 결과는 아닙니다.

실제 SSE가 화면에서 토큰별로 표시되는지, 로그아웃 후 비로그인 접근, 서버 재시작 뒤 기존 DB 보존은 별도 시험 항목입니다. AWS/Vercel 내부 설정 변경은 Aside 보고이며 Codex의 직접 화면 조작 결과가 아닙니다. 최신 라이브러리에서 TestClient/422 명칭의 deprecation 경고가 있었으며 테스트 실패는 아니었습니다.

## 과잉 여부

FastAPI·SQLite·JWT·최근 대화 컨텍스트·사용자 로그는 미션과 직접 연결됩니다. SQLAlchemy와 SSE는 필수 기술은 아니지만 이미 작동하는 구현이므로 제거·재작성할 이유가 없습니다. 여러 세션·통계·비밀번호 변경·풍부한 UI는 미션보다 넓은 기능이지만 첫 배포를 위해 더 확장할 필요는 없습니다.

현 단계의 적정 선택은 기존 구조 유지, 실제 불일치 수정, EC2 한 대, 정적 Vercel, 수동 BE 재배포입니다. Docker·RDS·로드 밸런서·Kubernetes·자동 배포를 추가하면 지금의 학습 목표보다 부담이 커집니다.
