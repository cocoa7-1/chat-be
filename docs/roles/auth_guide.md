## 현재 구현을 먼저 확인하기

가입에는 username·nickname·password가 필요하다. 비밀번호는 최소 8자이며 6자로 낮추는 실습은 제거했다. 닉네임과 비밀번호 변경 기능은 이미 있다. 현장 직책 role 컬럼은 현재 없으며 미션 필수 기능으로 단정하지 않는다. ChatMessage.role은 질문·답변 구분이다.

bcrypt는 암호화가 아니라 비밀번호 해시다. 원문을 복호화하지 않고 검증 함수를 사용한다. 해시가 있어도 짧고 흔한 비밀번호의 추측 공격 가능성이 사라지지는 않는다.

JWT는 서명으로 변조를 검사한다. 페이로드는 암호화된 비밀 보관함이 아니다. 현재 인증은 토큰 서명·만료뿐 아니라 DB 사용자의 존재·활성 상태도 확인한다. deps.py는 쿠키를 먼저, 없으면 Bearer 헤더를 선택한다. FE는 localStorage 토큰을 Bearer 헤더로 보낸다.

로그아웃은 서버의 인증 쿠키와 FE의 저장 토큰을 제거하는 동작이다. 이미 발급된 JWT를 서버에서 모두 폐기하는 기능과 구별한다. production JWT 키 최소 조건·요청 제한은 README에서 확인한다.

## 읽기·검증 실습

1. 격리 DB에서 가입 요청의 nickname 누락·짧은 비밀번호·중복 아이디 결과를 예측하고 기존 테스트와 비교한다.
2. 로그인 성공·실패를 따라가며 해시 확인과 토큰 발급을 구별한다.
3. 토큰 없음·만료·비활성 사용자에서 get_current_user가 어디서 401을 만드는지 설명한다.
4. 쿠키와 헤더가 함께 있을 때 선택되는 토큰을 코드로 확인한다.
5. 비밀번호 변경 뒤 이전 JWT와 새 로그인에 어떤 영향을 주는지 코드·실험으로 구분한다.

테스트 준비는 통합 가이드의 격리 원칙을 따른다. 토큰 구조를 볼 때는 가짜 예제 토큰을 로컬에서 해독한다. 실제 운영 토큰을 외부 사이트에 붙여 넣는 실습은 하지 않는다.

## 다음 개선을 정하는 질문

“서명 확인”과 “사용자 접근 허용”은 어떻게 다른가? 프런트와 서버가 분리됐다는 사실만으로 JWT가 필수일까? 직책을 추가한다면 가입 입력·모델·응답·기존 DB 변경 중 무엇이 필요한가?

확장 요구를 정하기 전에 현재 기능을 반복 구현하지 않는다. 작업 브랜치·실제 수정·검증 근거는 README의 협업 절차에 맞춘다. 고정된 10커밋 레시피는 사용하지 않는다.
